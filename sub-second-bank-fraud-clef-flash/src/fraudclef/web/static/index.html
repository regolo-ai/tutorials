How a payment is scored, and what the measurements changed

Steps on every payment

  1. Validate and pseudonymise. IBANs, names and device ids are replaced by keyed hashes before anything leaves the process.
  2. Compute features. Robust z-score of the amount against the customer's last payments (how many is set in the policy), velocity, impossible travel, new device, new beneficiary, Verification of Payee result.
  3. Apply hard rules. Sanctions, mule accounts, card testing, account takeover, limits. A match decides immediately.
  4. Pre-score. A weighted score of the features approves the clearly habitual payments.
  5. Ask Clef-Flash on Regolo. Only the grey zone, high amounts and instant transfers.
  6. Decide and record. Thresholds, overrides, PSD2 SCA exemptions, a fail mode per channel, then a hash-chained audit record.

What the measurements changed

  • Every question re-reads the whole state. Five questions cost about 6,100 input tokens and 566 ms; two cost about 2,500 tokens and 148 ms. The policy asks two.
  • Yes/no answers saturate. They come back as 0 or 1. The pattern choice and the 0–3 risk score return graded values, so decisions rely on those.
  • The shared API queues under load. At 4 parallel requests the model's median rose from about 200 ms to about 680 ms. Card-authorisation latency needs dedicated capacity.

Test payments

Set up a run in four steps: the policies, when to ask the decision model, the dataset. Then see how much fraud each setting stopped, how many genuine customers it interrupted, how long it took and what it cost.

    Which policies?

    A policy is the rulebook the engine follows, in a YAML file you can edit in Policies. One of its rules reads:

    Choose one, or up to three to compare them on the same payments.

    When should the decision model be asked?

    The decision model is Clef-Flash on Regolo: it reads the payment with the customer's history and answers the policy's questions with probabilities. Hard rules always decide first: a sanctioned country, a mule account or card testing is stopped before any model is asked. For everything else, the model adds what rules cannot see.

      Choose one, or more to compare them: for example only when needed against never.

      Which dataset?

      A dataset is a list of customers, each with their past payments and one new payment to check. Need another one? : written by a Regolo model, or sampled from IBM TabFormer.

          Policies

          A policy decides everything the engine does: hard rules, pre-score weights, when to ask Clef-Flash, the questions it asks and the thresholds for each decision. To adapt the engine to another kind of risk, create a policy and change those. The transaction format and the computed features are fixed in code.
